## 3. 术语与作用域：什么叫「assignee 任务权重排序」

**定义（唯一口径）**：给定 `(project, assignee, 筛选条件)` 三元组，把**落在该作用域内的卡**排成一个**由服务端决定、客户端只消费**的序，回答的问题是 —— **「这个 assignee 手上，下一张该看/该动的是哪张」**。

三点作用域约束（都要在实现里显式，不能靠默认）：

1. **只作用于「有 assignee 的卡」**。未分配池（`assignee_id` 为空）不是任何人的权重序；它在 S3 的候选清单里已有自己的桶（`reason: "unassigned"`），本契约不改。
2. **只作用于「非终态」卡**。`done` / `canceled` 是终态且不可逆（`src/core/domain/status.mjs#TERMINAL_STATUSES`），给它们算权重没有意义；默认过滤已由 `archived_at IS NULL` + 状态筛选承担，权重函数**不**对终态卡给分（给了也只是浪费算力）。
3. **不含 `epic` / `deploy` 类**（在**领取型**读上）。`src/core/domain/claim.mjs#AUTO_CLAIM_EXCLUDED_KINDS` 已把 `epic`（容器）与 `deploy`（部署卡）排除出自动领取；权重序**不得**把这两类顶到候选清单最前——否则等于绕过那条既有裁定。这是在**领读**上的约束；纯展示读（board/list）可以照常算序，但排序结果不应让 `epic` 因为「挡了很多下游卡」而占据第一屏（用 tier 兜底，§7.1 T1 说明）。

## 4. 因子清单（Acceptance ①）

**分两段：先硬后软。** 硬分层＝只回答「这张卡此刻能不能动」；软权重＝回答「能动/在等的那些里，先看哪张」。**层间不可逾越**，层内才加权。

### 4.1 硬分层（tier，线性扫描，不参与加权）

| 层 | 名称 | 定义 | 取值来源 | 判据（实读字段） |
|---|---|---|---|---|
| **T0** | 可动 | 球在 assignee 自己脚下 | `tasks.status`、relation `blocks` | `in_progress`（自己持有的在飞工作）；或 `todo` 且**全部前置卡都已 `done`** |
| **T1** | 停滞 | 卡在半路、需要自己出手去解 | `tasks.status`、`blocked_at`、relation `blocks` | `blocked`（自己声明的阻塞）；或 `todo` 但**存在未 `done` 的前置卡**（被依赖卡住） |
| **T2** | 在别人手上 | 自己无事可做，只能等/催 | `tasks.status`、`awaiting_reason` | `in_review`（已交付、待验收）；`awaiting`（E1–E5，停在人身上） |
| **T3** | 收口 | **不参与「待办」语义**的卡：沉到所有分层之后 | `tasks.status` | `backlog`（未排期）、`done` / `canceled`（终态）、以及任何**未知** `status` |

**T3 不是第四层语义，而是一个总函数的收口**（v1.1 补登，见 §14）：`T0`/`T1`/`T2` 回答的是「这张卡此刻能不能动」，而 `backlog` / `done` / `canceled`（以及未知状态）**不属于其中任何一层**。一个**偏函数**比较器对这些卡给不出答案，而「给不出答案」正是排序出错的经典起点。故补一行**收口层**把它们**沉到所有分层之后**：它们**不参与「待办」语义**（§3 约束 1/2 已把「未分配」与「终态」挡在作用域外，这里的收口是**同一立场的兜底**，不是新增语义）。**列集 / 分页不受影响**：T3 只决定「谁在前」，不新增列、不移动列归属、不改变筛选外延（§7.3）。**T3 的沉底不需要 Terry 拍板**——它是「这张卡根本不在待办里」的直接后果。

**为什么把「能不能动」做成层而不是权重**（这是本设计最重要的一条判断）：`todo` 但前置未完成，**在机制上就领不走、也动不了**（`listCandidates` 的 `allBlockersDone` 已是硬过滤）。把它做成一个「权重小一点」的因子，等于允许它**因为足够老而浮到最前**——恰好是最坏的结果：最前的位置被一张谁都不能动的卡占住。**语义约束必须硬，压力才软。**

**排序方向**：T0 在前，T1 次之，T2 再次，**T3（收口）沉到最后**。**T0/T1/T2 三层的先后已由 Terry 拍板**（方案 A，2026-10-29；另两个备选及未采纳理由见 §7.1）；T3 的沉底不在此列（见上一段）。理由：把「自己没得做」的卡（T2，尤其 `in_review`）沉到「自己有事做」之后，符合「这张清单是**待办**、不是**台账**」的立场；同时它们不会消失——层内仍按最久等待排，所以催办面（`web/src/lib/waiting-queue.js` 的 B27）依然是最久优先。

### 4.2 软权重因子（score，逐因子归一化到 `[0,1]`，方向一律「越大越靠前」）

| id | 名称 | 定义 | 取值来源字段 | 归一化 | 方向 | 适用条件 |
|---|---|---|---|---|---|---|
| **P** | 优先级 | 人类声明的相对重要性 | `tasks.priority`（`low\|medium\|high\|urgent`；前端域另含 `none`，见 §8 R2） | 序数线性：`rank / 3` ⇒ `none=.000 low=.000 medium=.333 high=.667 urgent=1.000` | 越紧急越靠前 | 常态；字段缺省 = `medium`（`src/core/domain/priority.mjs#DEFAULT_PRIORITY`） |
| **W** | 停留时长 | 在当前状态已停留的小时数（＝「卡在这一步多久了」） | `tasks.status_changed_at`；**为空回退 `created_at`** | 封顶比值：`min(小时 / 72, 1)` | 停留越久越靠前 | 非终态；**这是「创建时长」的更精确替身**，见 §4.3 |
| **A** | 建龄 | 自建卡起的小时数（Terry 点名的「创建时长」） | `tasks.created_at` | 封顶比值：`min(小时 / 720, 1)` | 越老越靠前 | 非终态 |
| **S** | SLA 压力 | 当前状态的已耗时 ÷ 该状态阈值，封顶 | `tasks.blocked_at`（blocked）/ `status_changed_at`（其余）+ **阈值参数表** | 封顶比值：`min(已耗 / 阈值, 1)` | 越接近/越过阈值越靠前 | **仅当该状态有阈值**；无阈值记 `0`（不是跳过、不是 NaN）。阈值见 §5.2 |
| **B** | 下游解锁 | 本卡完成后能解锁的**未完成**下游卡数（fan-out） | relation `blocks`：`src/core/storage/repositories/relations.mjs#listBlockedBy`（本卡为 `source`），逐个判目标 `status !== done` | `min(下游数 / 3, 1)` | 挡得越多越靠前 | 常态；上限 3，因为 0/1/2/3+ 是全部有意义的档位（`src/foundation/constants.mjs#TASK_ORDER_CAPS.unblocks = 3`；父卡 fan-in ≤ 8、链长 ≤ 8 是另一组图上限 `RELATION_FANIN_MAX` / `RELATION_CHAIN_MAX`，`blocks` 边本身无度数上限）。⚠ 关系**不在卡列表 wire 上**（见 §8 R16），故实现须用**一次聚合读**、不得逐卡回查（N+1） |
| **L** | 严重度（**可选，默认关**） | `sev:*` 标签的严重度 | `tasks.labels`（`sev:blocker\|critical\|major\|minor`，词表见 openclaw-team 的 ACL 指南 §15） | 序数线性：`rank / 3` | 越严重越靠前 | **默认权值 0**（即不参与），直到 labels 词表被机器校验（§8 R9）；无 `sev:` 标签 ⇒ `0` |

| `status_changed_at` | ✔ 同上 | `W`、`S` 的主时钟 |
| `blocked_at` | ✔ 同上 | `S`（blocked 态）的计时起点 |
| `priority` / `status` | ✔ 同上 | `P` / tier |
| `labels` | ✔ 同上 | `L`（可选） |
| `project` | ✔（`project_id`） | 作用域与 tie-break 末级 |

### 4.3 一处必须点名的冗余：W 与 A 高度相关，建议只留一个

`W`（当前状态停留）与 `A`（建龄）在**没换过状态**的卡上完全同时增长（`status_changed_at` 常空 ⇒ **回退**到 `created_at`）。同时保留两者的代价是**同一个信号被计了两次**（P .30 + W .25 + A .10 ⇒ 时间压力实际占 0.35），收益是能区分「老卡但刚动过」（W 小 A 大）与「新卡但卡住很久」（都小）。

**建议**：v1 保留两者（Terry 点名了创建时长，且区分能力真实存在），但**明确宣告二者的联合是 anti-starvation 预算**（§5.1）；若 Terry 想要更少的旋钮，**删 `A` 并把 .10 并入 `W`** 是等价改动的首选（比值封顶下两者形状相同，删掉只损失「刚动过的老卡」这一档区分度）。

## 5. 权值、区间与量级依据（Acceptance ②）

### 5.1 推荐权值向量（v1）

| 因子 | 推荐权值 | 合理区间 | 一句话量级依据 |
|---|---|---|---|
| `P` 优先级 | **0.30** | `[0.25, 0.40]` | 人类**声明**的意图，是全表唯一「不是从行为里推出来的」信号 ⇒ 必须是单项最大；但**必须小于时间压力之和**（见下） |
| `W` 停留时长 | **0.25** | `[0.20, 0.35]` | 状态机保证它**一定存在**（`status_changed_at` 每状态都有），是 anti-starvation 的主引擎 |
| `S` SLA 压力 | **0.20** | `[0.10, 0.25]` | 与 `W` 同向、但**依赖一个尚未定义的阈值表** ⇒ 定为次一级，阈值未定时它自动退化为 `0` |
| `A` 建龄 | **0.10** | `[0.05, 0.15]` | 与 `W` 冗余度最高的那只钟（§4.3）⇒ 只能拿「不重复计价」的小份额 |
| `B` 下游解锁 | **0.10** | `[0.05, 0.15]` | 图结构的涌现信号，稀少（多数卡 `0`）但一旦出现就是硬收益 ⇒ 与 `A` 同档 |
| `L` 严重度 | **0.05** | `[0.00, 0.10]` | 依赖一张尚未机器校验的词表 ⇒ **可选、默认关**，给了也只占零头 |

**Σ = 1.00**（恰好落在概率单纯形上）。

**量级依据（为什么是「这个数量级」，不是「这些具体数字」）**：

1. **归一化到 Σ=1 ⇒ 一项权值直接读作「占排序决策的百分比」**。这是选择「先归一化、再加权」而非「先加权、再归一化」的全部理由：`P=0.30` 的意思是「在满分 1 分的排序决策里，优先级占 0.30 分」，可审计、可辩论、可逐项签字；一个未归一化的 `P=30` 谁也说不出它到底多重要。
2. **单因子 ≤ 0.40** 是一条**隐含约束**：任何一项超过 0.40 就意味着它单独能压过另外两项之和，排序退化成「按那一项排」——那就不需要权重系统了。推荐向量的最大值 `P=0.30` 留了余量。
3. **`P < W + A + B + L`（0.30 < 0.50）是刻意设计的 anti-starvation 不变式**，不是巧合：一张 `low` 卡只要足够久（或挡人够多），**可以**压过一张崭新的 `urgent` 卡。**这是本设计最需要 Terry 明确同意的一条**——见 §5.3，它同时是一条**可测的命题**。
4. **相对排序的依据（一句话各自）**：`P`（声明意图）> `W`（状态机保证的钟）> `S`（依赖外部阈值的派生信号）> `A`（冗余的钟）≈ `B`（稀少但硬的图信号）> `L`（依赖词表的可选项）——统一按「信号的可靠性与独立性」降序，而不是按「Terry 提名的顺序」。

### 5.2 阈值参数表（S 因子的量纲统一）

`S` 唯一需要外部数字的因子。v1.0 时产品侧没有 SLA 阈值；**v1.3 订正：SLA 契约已内化**（`docs/sla.md` §2/§3），`src/foundation/constants.mjs#TASK_ORDER_SLA_HOURS` 取其状态可映射行。故：阈值仍**以参数表形式**引入，默认值与 `docs/sla.md` §2 对齐，其余**留空 ⇒ 记 0**（诚实：没定义就不假装有）。

| 卡的状态 | `docs/sla.md` §2 对应行 | 默认阈值 | 计时起点 |
|---|---|---|---|
| `blocked` | 「blocked 等待澄清」≤ 2h | **2h** | `blocked_at` |
| `in_review` | 「确认门等待复核」≤ 4h / 「产品验收排队」≤ 24h | **24h**（取宽口径） | `status_changed_at` |
| `awaiting`（E1–E5） | 「blocked 等待澄清」近似 | **24h**（无直接对应，取宽口径） | `status_changed_at` |
| `todo` / `in_progress` | **无对应行** | **无** ⇒ `S = 0` | — |

**两点必须说清的口径风险**：

- **`docs/sla.md` §3 的阈值是「工作时间」口径**（Asia/Shanghai 09:00–23:00，非工作时段顺延）。在一个零依赖的 core 里实现工作日历是**真实的工程量**，而该顺延规则本是**人工 patrol 的约定**、不是产品时钟。
  **建议（v1）**：`S` 用**墙钟**耗时，阈值按**墙钟**表达；工作日历列为 **v2 显式扩展**。⇒ 这会在工作时间口径下**提前**报压（夜里的 2h 其实是次日 2h）。**若 Terry 要求严格对齐 `docs/sla.md` §3，这是本设计唯一需要新增工程量的地方**，须在实现卡里单列。
- **阈值必须是可配置常量，不得散落在代码里**。落点见 §10.2。

### 5.3 敏感度：anti-starvation 是一个**可测的**开关，而推荐值恰好坐在它的临界点上

**实测**（§9.4 原始输出）：在 §9 的 6 卡样本上，只动 `P`、其余五项按比例重归一化，T0 层内的第一名在 `wP ≈ 0.29873` 处**易主**——此值以下由「久拖的 low 卡」领先，此值以上由「崭新的 urgent 卡」领先。推荐值 `wP = 0.30` 距该临界点仅 `0.0013`，两张卡在推荐向量下的分差是 **`0.001806`（0.18%）**。

⇒ **结论（这条要上报 Terry）**：`wP` 不是一个可以随便取整的旋钮，它是 **「久拖的卡能不能插队」的总闸**。取 `0.30` 意味着「**崭新 urgent 恰好多赢 0.18%**」；取 `0.29` 就翻面。**这正是要求 operator 拍板而不是由实现者默认的原因**，也说明为什么区间下界不能再低到 `0.25` 以下（`≤ 0.25` 时久拖卡稳定领先，等于关闭优先级）。

**三步校准法（离线、零依赖、可复现）**：

1. **冻结封顶值**：从团队**自己的**板历史（`taskctl export` 的产物）量出停留时长的 p50 / p90 / p99，把 `T_dwell_cap` 定在 **p99 附近**（推荐起点 72h）。理由：封顶的意义是「到达某个点时，再久也不再增加压力」——定在 p99 意味着只有约 1% 的卡会撞到天花板。建龄同理（推荐起点 720h/30d，与 §20 的 `A30` 同一量级）。
2. **有标注样本 + 网格搜索**：取一批「人类自己排过先后的」卡（例如 Elon 的历史 patrol 顺序、或 Team 手工标一个 top-3），在**推荐区间内**（不是整个单纯形）做网格搜索，目标函数取 **top-3 一致率**（比 Spearman ρ 更贴近实际用法：清单只有第一屏有人看）。
3. **取整**：在**接近最优的一组**里选**最圆的数**（0.30 / 0.25 / 0.20 / 0.10 / 0.10 / 0.05）。理由：可解释性优先于 0.3% 的排序收益——权重表是要被人读和改的。

**未跑声明**：步骤 1–3 本 lane **未跑**（需要板历史与人类标注，不在本卡的写面内）；本文件给出的是**程序**，不是**结果**。

### 5.4 权值的签核方式（供 Elon 上报）

建议 Terry 只回答 **3 个问题**，其余按推荐值随包发布：

1. **anti-starvation 要不要**（即 `P` 是否 < `W+A+B+L`）？要 ⇒ 用 `0.30`；不要（优先级必须绝对优先）⇒ `P ≥ 0.46` 或**把优先级提到硬分层里**（§7.1 的备选排法 C）。
2. **SLA 阈值用谁的口径**？墙钟（v1，省工程量、夜里会提前报压）还是严格对齐 `docs/sla.md` §3 的工作时间顺延（需新增工作日历）？
3. **可选项 `L`（sev 标签）开不开**？开则需先接受「labels 词表暂未机器校验」这一前提。

## 6. 合成公式与 tie-break（Acceptance ③）

### 6.1 合成公式

```
tier   = T(card)                       # §4.1，硬分层，0 = 最前
score  = wP·P + wW·W + wA·A + wS·S + wB·B + wL·L      # 每项已归一化到 [0,1]，Σw = 1
order  = sort by ( tier ↑, round3(score) ↓, <tie-break 链 §6.3> )
```

**为什么是线性加权（而不是分段 / 乘法 / 排序规则表）**：

- **可解释性**：每一分都能拆成「哪个因子贡献了多少」，这正是 `order_debug` 要投影的东西（§7.1 的参数表）。分段函数与乘法在这一点上迅速失控。
- **单调性**：线性 + 每个因子对时间是**单调不减**的 ⇒ **一张卡不会被自己的历史甩到后面**，也不会出现「越等越往后」的悖论。这是 anti-starvation 的数学前提。
- **无差序风险**：不需要「先按 A 排、A 相同再按 B」这类级联——那种写法会把「A 差一点点」和「A 差很多」压成同一档，从而让次因子压过主因子。线性加权不会（差额连续）。
- **代价（诚实说）**：线性加权允许**补偿**（一个极低的因子被另一个极高的因子抵消）。本设计**故意**保留这一点，只把不可补偿的那一类约束移出权重、放进 tier（§4.1）。

### 6.2 归一化：**封顶比值**，明确区别于 §20 的**秩归一化**

| | §20（PROJECTS） | 本契约（assignee task） |
|---|---|---|
| 方式 | **秩归一化** `(N − rank + 1) / N` | **封顶比值** `min(x / cap, 1)` |
| 一张卡的分取决于 | **同集内其它卡的位置** | **只有它自己** |
| 加一张卡会不会改别人的分 | **会** | **不会** |
| 排序可否下推 SQL（`ORDER BY <expr> LIMIT ? OFFSET ?`） | **不能**（需先取全量算秩） | **能**（**这是归一化的性质，不是落地选择**：v1.1 登记为「单口径 JS 排序」，见 §13.3） |
| 适用前提（§20 自己写的理由） | 「900 次活动的项目不该埋掉 3 次的新项目」——**N 很小（今天 N=3）** | **N 是几百张卡**，且要分页 |

**为什么为 task 分开走（这是对 §20 的有意偏离，不是抄漏）**：

1. **稳定性**：秩归一化下，往板里加一张卡会**改变所有人**的分数。若权重序被用来解释「为什么这张排第一」，那么「因为昨天有人建了一张卡」是**无法解释的答案**。
2. **分页**：Acceptance ④ 直接问「是否影响分页」。秩归一化**在结构上不能分页**（必须先看全集才知道秩）；封顶比值是**逐卡**的，因此 `ORDER BY` 可以整体下推到 SQLite，`limit/offset` 语义保持与今天一致。**这一条是选择归一化方式的决定性理由**。
3. **量纲统一的实现**：`[0,1]` 的封顶以「该因子的饱和点」定义，而不是以「集合内的相对位置」定义——饱和点在文档里是可引用的常数（72h / 720h / 3 张下游卡），因此**同一个数值在不同项目、不同 assignee 之间有可比性**（秩归一化没有这个性质）。

**§20 与本契约的共同点（刻意保留）**：服务端算序、客户端只消费；`order_debug` 诊断投影；archived/终态不参与；显示值四舍五入到 3 位小数。**只有归一化这一步分道**，且理由写在这里。

### 6.3 tie-break（并列打破）

**关键前提**：`score` 是浮点，直接比较几乎不并列。故**先四舍五入到 3 位**（与 §20 的 `round` 同一惯例）**再判等**——这样「并列」是一个**真实且可见**的事件（`order_debug` 里显示的分相同），tie-break 才有意义。

链（依次比较，前者相等才看后者）：

| 级 | 键 | 方向 | 依据 |
|---|---|---|---|
| 1 | `tier` | 升序 | §4.1 |
| 2 | `round3(score)` | 降序 | §6.1 |
| 3 | `priority` 秩 | 降序 | **卡面点名的规则**「priority → created_at 先后」的第 1 项 |
| 4 | `W`（停留时长） | 降序 | 「同分同时，先来先办」——比建龄更贴近「谁等得久」 |
| 5 | `created_at` | 升序（早的在前） | **卡面点名的规则**的第 2 项 |
| 6 | `status` 板序序号 | 升序 | 复用 `src/core/domain/enums.mjs#STATUSES` 的前 7 个（板列序），不另立词表 |
| 7 | `project_id`，然后 `identifier` | 升序 | **逐字复用** `src/core/storage/repositories/tasks.mjs#list` 的 `ORDER BY` 末两键 ⇒ 权重序与既有序在最后一键上**不可能分歧** |

**为什么末级要接到既有 `ORDER BY` 上**：`identifier` 在项目内唯一、`id` 全局唯一 ⇒ 整条链构成**全序**，与 `Array#sort` 是否稳定无关，也**不依赖** `LIMIT/OFFSET` 之外的任何约定。这是「稳定排序」要求（Acceptance ⑤）的最强形式：不是「碰巧稳定」，而是「**没有并列可稳**」。

**为什么把 `priority` 放在 `score` 之后又放一次**：`score` 里已有 `P`，但被其它因子补偿过；并列时用**未补偿的** `priority` 兜底，直白地兑现卡面「priority → created_at 先后」这句话。

## 7. 与既有排序 / 筛选 / 分组的交互（Acceptance ④）

### 7.1 是不是默认排序？——**是，而且没有别的序**（v1.4，operator decision）

**决定：权重序是唯一的序。** 任务列表读没有 `order` 参数；缺省、显式、任何调用方，拿到的都是权重序：

| 参数 | 值 | 语义 |
|---|---|---|
| `order_debug` | `1` | 逐卡投影：原始值、归一化值、加权贡献、tier、rank（**照抄** `/projects?order_debug=1` 的形状）。**投影是 opt-in，序不是**：不传就不返回 `order_debug`（§13.1） |
| 能力位 | `task_order: "weights-v1"` | 加进 `src/server/index.mjs` 的 `capabilities`（与既有 `project_order: "weights-v1"` 并列），供客户端**特性探测而非试探** |

**为什么改默认**（Terry 2026-10-29）：任务列表的用途是回答「这个 assignee 下一张该看/该动的是哪张」；而 `sort_order` 全仓没有写入方，板内默认序实际就是**创建顺序**——把最旧的卡排在最前，恰好与「先做该做的」相反。

**为什么连逃生口也删掉**（同一决定）：逃生口能给的只有「与时钟无关的确定性序」，而它没有实际调用方；客户端要这个序，可以从 wire 上已有的 `sort` / `created_at` / `project` / `identifier` 自己重建。留一个无人使用的排序参数，只会让「任务列表按什么排」有两个答案。

**v1.3 时「不设为默认」的三条理由，逐条处置**：

1. **默认序是既有契约**（导出依赖它）→ 导出直读仓库层 `tasks.list`，不经过列表读，字节不变（§10.2 断言 8 仍守着）；仓库层的 `sort_order, created_at, …` 序仍是本契约 tie-break 的末级，只是不再作为列表参数暴露。
2. **权重序是时间相关的**（§8 R5）→ 接受：同一输入、同一 `now` 仍是全序；跨时刻的差异正是「压力随时间变化」要表达的东西。
3. **UI 面在原型上是空地**（§2 末段）→ UI 消费服务端返回序，**不改原型即可获得权重序**；原型上的**排序说明**仍是另一个设计轮次，不在本契约内。

**tier 的先后（已拍板：方案 A，Terry 2026-10-29）**：

### 7.3 与筛选、分组、分页

- **筛选**：**不变**。权重序作用在**筛选之后**的集合上（先筛后排，无例外）。理由：筛选是「用户要什么」，排序是「先看哪个」，后者不改变前者的外延。
- **分组**：**不变，且权重只在组内生效**。当前唯一的分组是看板的状态列，而列由 `stage` 决定——**权重永远不移动一张卡所属的列**（tier 也不移动；tier 只定「组内谁在前」）。若将来加「按 assignee / label 分组」，同上：先分组，组内用权重序。
- **分页**：**语义不变**。因为归一化是**逐卡**的（§6.2），整个排序键都能表达成一个 SQL 表达式 ⇒ `ORDER BY <expr> LIMIT ? OFFSET ?` 在**结构上**与今天同构。**唯一的硬约束**：排序键必须**确定性**，故 §6.3 的末两键（`project_id, identifier`）**必须**进排序键，否则分页会在同分卡之间漏/重。
  ⚠ **落地口径（v1.1，§13.3）**：**作用域（筛选）下推 SQL，排序键（`ORDER BY`）未下推**——先按 §8 R16 把作用域（`status` / `assignee` / `unassigned`）下推进 SQL 且**不截断**，读回**整个作用域**后在 **JS** 里用**一份** comparator 排序，再切页。⇒ 上段的「可表达成 SQL 表达式」是**归一化的性质**，**不等于**「已在 SQL 里下推」。保持单口径的理由见 §13.3。
  ⚠ **但 v1.0 时的候选读是「先截断、后过滤」**（`listCandidates` 读 `list({status:"todo"})` 默认 `limit = 200`，再在 JS 里按 assignee 过滤）⇒ 排序若建在截断后的集合上，就是「在错的一页里排得整整齐齐」。本契约要求**先把作用域下推到 SQL**（见 §8 R16），这也是 §6.2 选逐卡归一化的直接收益。
  **v1.1 状态：已收口** —— `T-20261014-043124` 已把作用域（`status` / `assignee` / `unassigned`）下推进 SQL 且**不截断**（`limit: null`），故上一句从「本契约要求」变成「已落地」（`CHANGELOG` 同句记录：`T-20261014-061937`）。见 §12 U9 与 §13.3。
- **`awaiting` 覆盖态**：`awaiting` 卡其 `stage` 仍是 `in_progress`（`web/src/stores/board.js#stageOf`），故它**不新增列**；本契约在 tier 里把它归 T2。**列内与 waiting 视图的分工不变**。

### 7.4 与 supervisor 派发的耦合（**最重要的一条交互**，也必须点名）

`src/shared/scheduling.mjs#planTick` 的输入就是**候选清单**，而它**按给定顺序**依次 wake，直到并发上限（`maxConcurrency`）。⇒ **候选清单的顺序 = 派发优先级**：排在前面、且在名额内的卡**会被真的唤醒**，后面的只能等下一轮。

**这条把「权重排序」从一件 UI 小事变成一件能改变团队行为的事**：

- **正面**：这是权重排序真正值钱的地方——在 v1.4 之前，「哪张先被唤醒」等于板子的列表序，而那只是**创建顺序**（§2 S1a）；v1.4 起列表序与派发序合为一条，权重序让「先做该做的」在**派发层**直接生效。
- **风险（必须上报）**：一个错的权值向量会**静默改变团队派发**，而且不会报错、不会红测试——只会表现为「最近总在做某些卡」。v1.4 起权重序是**唯一的**列表序，这条风险因此**扩大**（每一轮 tick 都按权重派发，没有运行时开关可退回）。⇒ 护栏：①**权值可回溯**——能力位 `task_order` + `order_debug=1` 让「为什么是这张被唤醒」逐卡核对；②**先小样本校准**（§5.3）；③权值向量集中在 `src/foundation/constants.mjs`，怀疑派发异常时回退 = 改权值并发布，而不是翻一个运行期开关。
- **边界**：本契约**不**改 `planTick` 本身，也不改 supervisor；它只决定喂给它的**候选数组的顺序**。

### 7.5 与既有 `DESIGN.md` §20 的关系（一句话）

§20 管**项目**（侧栏那一列），本契约管**卡**（板/列表/候选）。两者**同构不同参**：同构 = 服务端算序 + 客户端消费 + `order_debug` + 3 位小数 + 终态沉底 + **各自是所在面的唯一序**；不同参 = 归一化方式（§6.2）与因子集。

| **R15** | **`blocked_at` 离开 blocked 后不清空**（它是「最近一次进入 blocked 的时刻」，`src/core/storage/repositories/tasks.mjs#moveCas` **只在 `to === "blocked"` 时写入、任何离开都不清**） | 同左（实读 `moveCas`：`if (to === "blocked") { sets.push("blocked_at = ?") }`，未见清除分支；对比 `awaiting_reason` 是**每次 move 都重写**、离开即清） | **S 因子的 `blocked_at` 分支必须被 `status == "blocked"` 严格门住**。若实现漏了这个门，一张「三个月前被阻塞过一次、早已解阻」的卡会带着三个月前的时间戳拿到 `S = 1.0` 而插到最前——**静默、无报错**。⇒ 实现与 C3 都要有一条断言：「非 blocked 卡的 `S` 只走 `status_changed_at`」 |
| **R16** | **卡列表 wire 不携带依赖数**，且既有候选读**先截断再过滤** | 关系是 `task_relations` 的 `blocks` 边，**不在**卡列表的 wire 字段里（`src/shared/wire.mjs#taskToWire` 无此字段）；`src/core/commands/tasks.mjs#listCandidates` 是 `list({status:"todo"})`（**默认 `limit = 200`**）**之后**才在 JS 里按 assignee 过滤 | ① `B` 因子**必须**用一次**面向该作用域的聚合读**（`listBlockedBy` 按卡批量取），**不得**逐卡回查（N+1）；② **截断先于过滤**是**既有**的缺陷，不是本契约引入的——但权重序若建在截断后的集合上，就会「在错的一页里排得整整齐齐」。⇒ C2 的实现卡**必须**把读的**作用域（assignee/project + status）下推到 SQL**，再在**未截断的**集合上排序/分页（这正是 §6.2 选逐卡归一化的收益），并把这条列为一条**独立断言**。**v1.1：已落地**（`T-20261014-043124`），见 §7.3 与 §12 U9 |

**边界之外（本契约明确不管）**：`done`/`canceled` 的排序；跨项目的全局序；`web/` 的 UI 呈现（开关长什么样、放哪里）；提醒/通知的触发（那是 `monitoring/` 与 supervisor 的地盘）；以及**任何权值以外的实现细节**。

### 10.2 C3 可写成的断言（全部**不依赖浏览器**，因原型无此面）

1. **纯函数**：给定固定样本与固定 `now`，`order()` 返回**逐字节相同**的数组（同一输入两次调用同序）。
2. **tier 优先于 score**：构造一张 T2 卡使其 `score` 严格高于所有 T0 卡，断言它仍排在**所有** T0 卡之后（§9.3 第 1 条）。
3. **anti-starvation 临界点**：断言 `wP=0.30` 时 `A1 > A3`、`wP=0.20` 时 `A3 > A1`（§9.4）——即断言**产品行为**，不是断言常数。
4. **缺失字段不产 `NaN`**：`status_changed_at=""`、`blocked_at=null`、`labels=[]`、`priority="none"` 四种输入下，`score` 是有限数且序可复现（§8 R4/R2）。
5. **单调性**：固定卡，把 `now` 往后推任意大，断言 `score` **不下降**（§8 R6）。
6. **末级全序**：构造两张 3 位分相同的卡，断言序由 `priority → W → created_at → status → project_id → identifier` 决定（§6.3）。
7. **列表读就是权重序**：`/tasks` 与 `/tasks/candidates` 的响应序就是权重序，且与 `repos.tasks.list` 的仓库层序**不同**（证明权重逻辑真的生效）；请求里带 `order=` 会被忽略（该参数不存在，§7.1，v1.4 起）。
8. **导出不受影响**：`md` 导出字节不变（§2 S1 的承诺）。
9. **`blocked_at` 的门**（§8 R15）：一张 `status != "blocked"` 但带**很久以前** `blocked_at` 的卡，`S` **不得**由 `blocked_at` 得出（否则它会凭一个陈旧时间戳插到最前）。
10. **作用域先于排序**（§8 R16）：断言「某 assignee 在 `limit=N` 下的返回」与该 assignee **全集**的前 N 名一致——即证明读没有被截断在排序之前。

## 13. (a) 三项口径登记（v1.1，实现落地后补登）

> **为什么要有这一节**：这三条在 v1.0 契约里**没有被显式定义**。实现卡（`T-20261014-043124`）必须自己拿主意 —— 而**拿主意的结果必须是可查的口径**，不能是「代码里就是这么写的」。故在此**逐条登记**：每条给出**实读锚点**，a1/a2/a3 另附本 lane 的一次**实跑探针**（`workspace/T-20261014-063700/a-probe.mjs`，输出 `a-probe.log`；`node` 属 `docs/docker.md` §Host-allowed checks 的宿主允许项）。**本节不回改 v1.0 的任何结论**。

### 13.1 a1 —— `order_debug` 只决定**是否返回投影**，不改变序（v1.4 重写）

**口径（两条）**：

1. `order_debug` 为**真**（`1` / `true` / `yes` / `on`，与 `include_archived` / `stale` 等既有开关同一判定）⇒ 响应带 `order_debug` 数组；为假或缺省 ⇒ 不带该 key。**序不受影响**——列表读永远是权重序。
2. **`order` 参数不存在**（v1.4 起）。带上它会被当作未知查询参数忽略：不报错、不换序。

**为什么改**：v1.1 时权重序是 opt-in，`order_debug` 顺带选中它是必要的（否则投影与序不同源）。v1.4 把权重序设为唯一序后，这个联合语义退化成一句话：诊断开关只加投影。

**实读锚点**：`readOrdered` / `orderedCandidates` 都以 `debug = orderDebug === true` 计算投影；`resolveOrder`、`TASK_ORDER_MODES`、`TASK_ORDER_DEFAULT` 已删除；`src/server/routes/tasks.mjs` 的 `LIST_QUERY` 只剩 `order_debug`。

**v1.1 探针（历史，v1.4 起不再成立）**：

| 请求 | v1.1 观测 | v1.4 之后 |
|---|---|---|
| `order=board` | `orderDebug = null` ⇒ 板序路径 | 该参数不存在，请求按权重序返回，`orderDebug = null` |
| `order=board&order_debug=1` | `orderDebug = 数组(12)` ⇒ 权重序（debug 胜出） | 同上：权重序 + 投影数组 |
| `order=bogus` | 抛 `VALIDATION_FAILED` | 参数不存在 ⇒ 不抛，按权重序返回 |
| `order=bogus&order_debug=1` | 不抛，权重序 + 投影 | 同左 |

**契约侧结论**：序只有一个（权重序）；`order_debug` 是一个纯附加的投影开关。实现与 C3 据此断言。

### 13.2 a2 —— 投影覆盖**整个 ranking**（并据此计入 §8 R12 成本）

**口径**：`order_debug=1` 返回的 `order_debug` 数组覆盖**整个作用域的排序结果**，**不是当前页** —— `limit` / `offset` 只切 `tasks`，**不切投影**。

**为什么这是对的**：投影回答的是「**这张卡为什么在这个位置**」，而这个答案**必然**要引用它赢过、输给的那些卡。把投影按页切等于把「它赢了谁」删掉，投影就退化成「它自己的因子值」，也就答不出 §8 R11 承诺的那个问题。

**为什么必须登记到成本上（计入 §8 R12）**：`order_debug=1` 的成本 = **整个作用域的排序 + 整个作用域的投影**，**与 `limit` 无关**。⇒ 诊断开关**不得**出现在轮询路径上（轮询**不带** `order_debug`）。这条附注已写进 §8 R12 的处置。

**实读锚点**：`src/core/commands/tasks.mjs#readOrdered` 返回 `orderDebug: debug ? ranked.map(taskOrderDebugEntry) : null` —— `ranked` 是**排序后的全集**，`page` 只喂给 `tasks`；函数内注释逐字：「The projection covers the whole ranking, not the page — the question it answers is "why is this card where it is", and that needs the cards it beat.」候选读（`orderedCandidates`）同构。

**实跑（探针）**：12 张卡的作用域、`limit=1` ⇒ `tasks` 长度 **1**，`order_debug` 长度 **12**。

### 13.3 a3 —— 排序键（`ORDER BY`）**未**下推 SQL（**单口径优先**）

**口径**：权重序的**作用域（筛选）进 SQL**，**排序键不进 SQL**。执行上是两步：

1. **筛选进 SQL、且不截断** —— `status` / `assignee` / `unassigned` 下推成 `WHERE`，并带 `limit: null`（SQL 里**没有 `LIMIT`**）：这正是 §8 R16 的收口；
2. **排序在 JS** —— 读回**整个作用域**后，由**一份** comparator（§6.1 / §6.3 的 `tier` → `round3(score)` → 7 级链）产生权重序，**再**切页。

**「单口径优先」是这个选择的名字**：若排序键同时存在于 SQL 表达式与 JS comparator 里，**同一个序就有了两份定义**，而 §6.3 要求七级链（含末两键的确定性）在**每一份**里都对 —— 两份定义漂移是**静默**的（两边各自自洽，只有「SQL 序」与「JS 序」不一致时才暴露，而那正是分页漏/重的现场）。故取**一份实现**：排序只在 JS 里定义一次。

**代价（诚实说，已计入 §8 R12）**：整个作用域要**读回内存**再排。§8 R12 的实测因此有两条边界：**千卡量级是十毫秒级**（可接受），但**随作用域线性增长**，且这不因「有没有 `LIMIT`」而改善。

**两处措辞必须先钉住**（否则会把「性质」读成「已落地」）：

- §6.2 表里「排序可否下推 SQL … **能**」问的是**归一化的性质**（**逐卡** ⇒ 整个排序键**可**表达成一个 SQL 表达式）——**性质仍成立**；本登记说的是**落地选择**：没有这么做。
- §7.3 的「分页」条目已按同一口径改写（见该节 ⚠ 段）。

**实读锚点**：`src/core/commands/tasks.mjs#readOrdered` —— `const scoped = ctx.repos.tasks.list({ ...scope, limit: null })` 之后才 `orderTasks(withRelationCounts(scoped, counts), …)`；`src/core/storage/repositories/tasks.mjs#list` 在 `limit: null` 时**去掉 `LIMIT` 但保留它自己的 `ORDER BY sort_order ASC, created_at ASC, project_id ASC, identifier ASC`**（S1 板序）—— **权重键不在其中**。

**实跑（探针，抓 `db.prepare` 实际收到的 SQL）**：

| 观测项 | 权重序路径 | 板序路径 |
|---|---|---|
| `WHERE project_id = ?`（筛选进 SQL） | **有** | 有 |
| `LIMIT` | **无**（§8 R16：不截断） | 有 |
| 权重键（`tier` / `score` 表达式） | **无** | — |
| `ORDER BY` | 只剩 S1 的板序（随后被 JS 整体覆盖） | S1 板序 |
