# Intake — a human's description becomes work

A human submits a description instead of a filled form. The matter is a decision:
what work does this description name, and which role owns each piece?

## What you receive

- the description, in the human's own words;
- the project it was submitted to;
- the submitting human, who is the reporter of every card you file.

## Decide the work

Adopt the project's canonical shape when it has one: its graph document names the
epic, the stages and the edges, and an existing instance is the pattern to reuse.
Otherwise split the description into one or more **deliverables** — each one thing
a role can land alone and leave the tree coherent. A scope of work the description
leaves outside itself is E1: escalate it, and file what the description names.

Each card carries:

- one accountable role from the routing table;
- a target, so two cards claim two scopes;
- acceptance seeded from the outcome the description asks for;
- the submitting human as reporter;
- the request's id in its metadata, so a later pass finds the card again.

## Record the outcome

When the cards exist, record the request as consumed with their identifiers. The
request's id in each card's metadata is what lets a later pass recover cards from
an interrupted decision; complete a partial result, and reuse it.

A description that names no work is a recorded refusal: state what the human can
send instead. The refusal is the human's answer, so make it specific.

## Boundaries

The cards are the decision. Claims, execution and closure belong to the roles and
the board. The human's own submission is the authorization to file cards; record
it and move on.
