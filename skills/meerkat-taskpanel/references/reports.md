# Periodic reports & statistics

Daily / weekly / monthly reports over the board, generated by `scripts/report.mjs`. This is
the **period** report — an aggregate over cards finished in a window. It is **not** the
per-card delivery report the delivery gate asks for; that one is `cli.md` §`report`.

The feature is deliberately **domain-agnostic**: metrics are named and grouped by you, through
a grouping dimension plus `namespace:value` label filters. The shipped `software` preset is an
example, not the shape of the feature.

## Report spec

Every report has the same five sections:

| Section | Written by | Content |
|---|---|---|
| **Overview** | generator | The window and the number of cards completed in it. |
| **Core metrics** | generator | One row per metric label (preset) or per grouping value (no preset). |
| **Key decisions & milestones** | you | A `TODO` the author replaces. |
| **Risks & blockers** | you | Same. |
| **Next period plan** | you | Same. |

## Measurement rules

**Data source.** One existing read — no new backend query:

```bash
node scripts/run.mjs issue list --json --limit 1000 --include-archived [--project <id>]
```

`--include-archived` matters: a card is archivable 7 days after it becomes terminal, so a
monthly report that skipped the archive would silently drop work finished earlier in the month.

**Completion window.** A card counts when **both** hold:

1. `status === "done"`, and
2. `status_changed_at` falls inside the window.

`status_changed_at` is a stored timestamp, not a computed one: a reopened and re-closed card
carries the latest close, and a `done` card with no usable timestamp never counts. The window
is **half-open** (`start` included, `end` excluded), so adjacent windows tile without
double-counting midnight.

**UTC only.** A UTC day, a UTC ISO week (Monday 00:00 → next Monday) or a UTC calendar month. A
card completed at `2026-10-31T23:30:00Z` belongs to October wherever it is read. `--date` may
be any day inside the window.

**Grouping dimension** — `--group-by`:

| Value | Bucket key | Missing value |
|---|---|---|
| `kind` *(default)* | the card's `kind` (`task`, `epic`, `deploy`) | not counted |
| `project` | `project_id` | not counted |
| `assignee` | the assignee's `display_name`, falling back to `id` | not counted |
| `status` | the card's `status` | not counted |
| `label:<namespace>` | the value of the first `<namespace>:` label | not counted |

`label:<namespace>` is general; the reserved namespaces are `category:` (kind of work),
`area:` (part of the product), `env:` (`prod` marks production), `sev:` (severity). Namespaces
match case-insensitively and in full (`categoryx:` does not match `category:`); buckets are
lower-cased, so spelling never splits a bucket. A card with no value for the dimension is
uncategorized — not counted, not folded into a bucket.

**Metrics and presets.** A **metric** is a named count built from a grouping dimension and a
set of `namespace:value` filters (`where`, and optional `without`). A **preset** bundles a
default grouping dimension, excluded kinds and a list of named metrics under one name:

| `software` metric | Filter |
|---|---|
| Requirements handled | `category:req` |
| Development tasks completed | `category:dev` |
| Bugs fixed | `category:bug` **and not** `env:prod` |
| Production incidents | `category:bug` **and** `env:prod` |

Grouping is `label:category`, and epics are excluded — a container is not delivered work. To
define another preset, add an entry to `PRESETS` in `scripts/report.mjs` (same shape); no code
change is needed for a different domain's metric names.

**Counting rules.**

- A card must be `done` and completed inside the window, and must carry the grouping value.
- A preset's `excludeKinds` are dropped.
- **A card is counted once** — `total` is the number of counted cards. Metric counts may
  overlap and need not sum to `total`; `counts` (the grouping map) always does.
- Ordering is stable: completion time, then identifier.

## Commands

Run from this skill's directory:

```bash
node scripts/report.mjs --period daily
node scripts/report.mjs --period weekly --date 2026-10-07 --group-by label:area --json
node scripts/report.mjs --period monthly --date 2026-10-09 --project demo --preset software
node scripts/report.mjs --period weekly --assignee linus --group-by project
```

Options: `--period daily|weekly|monthly` (default `daily`), `--date YYYY-MM-DD`, `--project
<id>`, `--assignee <name>`, `--group-by kind|project|assignee|status|label:<ns>`, `--preset
<name>`, `--limit <n>` (default 1000), `--json`, `-h`.

Markdown is the default output. `--json` prints `{"ok":true,"data":{"summary":…}}`, whose
`summary` carries `counts`, `metrics` (or `null`), `total`, the resolved `window`, and the
completed-card list (`identifier`, `title`, `assignee`, `group`, `metric`, `completedAt`).

Failures exit `2` for a usage problem and `1` for a runtime one. Bind to **`error.code`**:
`INVALID_PERIOD`, `INVALID_DATE`, `INVALID_LIMIT`, `INVALID_GROUP_BY`, `INVALID_PRESET`,
`DATA_SOURCE_FAILED`, and the board's own codes passed through.

## Template

The generator prints this shape with every placeholder filled. Daily, weekly and monthly differ
only in the window wording (`{{period_start}}`, plus `{{period_end}}` for weekly/monthly):

```markdown
# {{period_label}} report — {{project}}

> One **{{period_label}}**. Every number below covers {{period_start}}
> {{period_end}} (UTC), and every listed card was completed *within that window*.

- Period: {{period_start}} {{period_end}} (UTC)
- Project: {{project}}
- Grouped by: {{group_by}}
- Output language: chosen to follow the current user's language habit.
- Generated at: {{generated_at}}

## Overview

- Total completed: {{total}}

_Write one or two sentences on the period's shape._

## Core metrics

{{core_metrics}}

### Completed cards

{{completed_cards}}

## Key decisions & milestones

- TODO: the decisions taken, and the milestones reached.

## Risks & blockers

- TODO: what is slowing the team down right now.

## Next period plan

- TODO: what the next report should be able to claim as done.
```

When a preset or an assignee filter is in force, the generator adds a matching `- Preset: …` /
`- Assignee: …` line to the header block.

The `- Output language:` line is the one rule about prose: **the report is written in the
current user's language habit**. The generator emits the English skeleton verbatim and
translates nothing; the author writes the `TODO:` sections in the reader's language.
